드론 탐지장비(레이더·RF 스캐너 등)가 보내는 데이터를 **UDP로 수신 → 지도에 실시간 표시 → 바이너리 로그로 저장 →
그대로 리플레이**하는 Windows 데스크톱 모니터링 시스템입니다. 2023년 12월부터 통신 프로토콜, 데이터 파이프라인,
지도 시각화, 로그 시스템, UI까지 전 영역을 단독으로 설계·개발하고 유지보수하고 있습니다.

## 왜 필요했나

- 탐지장비가 주는 값은 숫자·좌표의 나열이라, 드론이 어느 방향·거리에 있는지 직관적으로 파악하기 어렵습니다.
- 탐지 이벤트를 남기고 다시 분석할 방법이 없어 오탐/실제 위협 여부를 사후 검증하기 어려웠습니다.
- 서로 다른 장비(탐지장비, GPS 기준국 등)가 제각각 데이터를 보내 한 화면에서 통합해 볼 수 없었습니다.

## 핵심 기능

- **실시간 모니터링** — 기준 장치 위치, 탐지된 드론의 위치/속도, 탐지장비의 위치·방위각을 지도 마커로 표시
- **경보 구역(Zone) 관리** — 기준 위치로부터의 거리로 4단계 경보 구역을 판정(반경은 설정 파일로 조정)
- **통신 두절 감지** — 일정 시간 패킷이 없으면 마커 색상을 바꿔 경고
- **바이너리 로그 & 리플레이** — 수신 데이터를 고정 크기 포맷으로 저장하고, 실제 수신 간격(또는 배속)대로 재생하며 궤적과 위치 오차 차트를 함께 확인
- **로그 언패킹** — 바이너리를 탭 구분 텍스트로 변환해 엑셀 등에서 분석
- **모의 송신 시뮬레이터** — 하드웨어 없이 통신 프로토콜을 검증
- **KML 연동** — 관심 구역 경계·경로를 지도에 오버레이

## 아키텍처

```
[탐지장비 / 모의 시뮬레이터]
      │ UDP 패킷 (자체 정의 프로토콜)
      ▼
통신 계층 (DMLink)  UdpTransport → 패킷 워킹 → CRC 검증 → 메시지 역직렬화 → 이벤트 발행
      ▼
애플리케이션 (MVVM)  이벤트 → 통합 데이터 모델
      ├──────────────► 지도 시각화 (DMGMap)  마커·경로·존 렌더링
      └──────────────► 로그 계층  바이너리 기록 / 비동기 리플레이 엔진
```

통신(DMLink)과 지도 렌더링(DMGMap)을 메인 앱과 분리된 **독립 라이브러리**로 설계해, 같은 통신 코드를 메인 앱과
시뮬레이터가 함께 쓰고, 새 메시지·마커 타입을 추가할 때 영향 범위가 한정되도록 했습니다.

## 주요 설계 결정

- **UDP + 자체 바이너리 프로토콜** — 실시간 위치 데이터라 연결 수립이 없는 UDP를 택했고, `[동기][길이][그룹ID][메시지ID][카운트][페이로드][CRC]`
  구조의 경량 패킷을 직접 설계했습니다. 동기 바이트로 경계를 찾는 비동기 패킷 워커와, 룩업 테이블 기반 **CRC16-CCITT** 검증을 구현했습니다.
- **고정 크기 로그(레코드당 117바이트)** — 순차 읽기만으로 빠르게 재생하고 별도 인덱스가 필요 없습니다. 대신 필드를 추가하면 기존 로그와
  호환이 깨지는 트레이드오프가 있어, 파일 헤더에 **버전 문자열**을 넣어 구분합니다. 구간 이벤트 마커도 같은 레코드 포맷의 타입 값만 바꿔 기록합니다.
- **비동기 리플레이 엔진** — `async/await` + `TaskCompletionSource`로 일시정지/배속 변경이 UI 스레드를 막지 않고 즉시 반영됩니다.
- **SSH 터널 경유 DB 접근** — 계정 정보 DB(MongoDB)는 직접 노출하지 않고 SSH 터널로만 접근합니다.

## 트러블슈팅

| 문제 | 원인 → 해결 |
|---|---|
| 제어 명령 지연/무응답 | 스핀락 대기로 CPU 점유·타이밍 문제 → 블로킹 대기로 교체 |
| 로그인 후 세션 잔류 | SSH 연결 미정리 → 로그인 완료 시 명시적 해제 |
| 리플레이 로그 불러오기 크래시 | 예외 처리 누락 → 보강 및 재현 케이스 기반 수정 |
| 지도 타일이 안 뜸 | 지도 API 키 만료 → 키 교체, 만료 모니터링 필요성 인지 |
| 단위 불일치(m ↔ cm) | 저장·언패킹 시점의 변환 혼재 → 저장은 원본 단위(cm), 표시 변환은 언패킹 한 곳으로 책임 통일 |

## 배운 점

고정 크기 로그는 성능을 주는 대신 필드 추가 때마다 호환성을 고민하게 했습니다. 다음에는 가변 길이 포맷이나 버전 마이그레이션 전략을
처음부터 설계하고 싶습니다. 또 기존 이벤트 기반 싱글톤 구조를 유지하면서 신규 기능은 `CommunityToolkit.Mvvm`·`WeakReferenceMessenger`로
점진 전환하는 경험을 쌓았습니다.
